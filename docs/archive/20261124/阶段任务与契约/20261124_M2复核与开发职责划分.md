# M2复核与开发职责划分

日期：2026-11-24。本文用于M2收口期间的协作边界，不改变M2需求、验收标准或M3准入条件。

## 一、我的职责：复核与验收

我负责独立判断“交付是否满足要求”，不负责替开发补写实现。

### 我可以做

- 读取任务书、修复记录、源码、测试脚本和浏览器证据，检查是否相互一致。
- 启动隔离的本地样板、Mock服务和浏览器，执行既定验收路径。
- 新增或调整验收脚本、断言和可读复核记录，但只为验证行为，不替代产品实现。
- 检查PDF夹具hash、请求／锚点身份、来源有效性、题目隔离、草稿恢复和失败状态。
- 运行 `npm test`、构建、指定浏览器回放及其他与验收直接相关的测试。
- 对每项给出“通过／修改／暂缓”，记录实际操作、证据、失败和未覆盖范围。
- 发现需求、实现、报告不一致时指出具体文件、状态和复现步骤。
- 维护验收文档和唯一开发计划中的状态，但不把开发自述改写成通过。

### 我不可以做

- 不在没有开发交付的情况下直接修改正式业务逻辑来“让测试通过”。
- 不把静态占位、预写回答、硬编码状态或Mock结果当成真实能力通过。
- 不代用户签收视觉满意度、中文输入体验或学习效果。
- 不代填人工质量评分、`human_reviewed`、`development_passed` 或用户确认。
- 不调用新的真实模型、不发送个人资料、不扩大预算，除非有单独明确授权。
- 不因测试方便删除用户内容、正式记录、失败证据或unknown账单。

## 二、开发职责：实现与证据

开发负责把未通过项修到可重复验证，并交付足够证据。

### 开发必须做

- 根据复核结论修改源码、契约、样板和必要的测试；每项改动写明影响文件。
- 先补确定性状态和身份逻辑，再补视觉和浏览器矩阵；不得只改提示文案绕过状态问题。
- 为每个修复增加可重复的单元、API或浏览器断言；断言应检查真实目标状态，不只检查通知文字或写死的 `data-*` 标记。
- 对PDF显示报告真实 loading／ready／failed；若只能验证字节读取，必须明确写成字节读取，不能称像素渲染通过。
- 对资料、题目、请求、来源版本和解释目标使用稳定身份；禁止用当前页面或一个全局布尔值代替冻结对象。
- 修复后运行与改动相关的维护命令，并保存原始输出、截图、失败日志和测试版本。
- 更新修复记录，列出已通过、未运行、仍限制和下一步，不删除旧失败证据。
- 在请求进入真实模型前，先提交隔离Mock和浏览器证据；真实调用须另有素材、模型和预算配置。

### 开发不得做

- 不进入M3真实接入，除非M2复核记录明确写出准入并得到用户确认。
- 不把浏览器默认100%视为原生125%，不把viewport矩阵视为中文IME或Tab验收。
- 不把预写讲解、题目B的通用文案或静态迟到说明当成真实请求隔离证明。
- 不把任务A的解释通过当前视图带到任务B；不把来源失效状态通过导航重新置为有效。
- 不把失败重试和已发布回答续写混成同一种请求；不自动重发unknown请求。
- 不修改正式库、正式笔记、正式评分或旧记录来适配样板。

## 三、双方工作流

1. 开发提交修复记录、源码差异、测试命令和证据目录，并明确“本轮未做什么”。
2. 我先只读检查报告与源码，再运行隔离验证；发现失败时给出最小复现，不直接替开发猜修复方案。
3. 开发根据复现修复并补测试；修复范围扩大时更新影响清单，不静默改变M2目标。
4. 我重新运行原失败路径和相关回归，分别记录通过、失败、环境阻塞和未覆盖。
5. 只有M2所有必要项有证据且用户完成产品层确认，才写“进入M3”；否则保持“M2待收口”。

## 四、当前分工

### 我现在做

- 复核R1～R5的证据边界。
- 运行已有M2回放、构建和前端测试，并记录结果。
- 设计并执行剩余验收：原生125%、Tab顺序、Escape／焦点、中文组合输入、真实PDF渲染、迟到事件隔离。
- 输出“通过／修改／暂缓”结论，不修改M2业务实现。

### 开发现在做

- 继续准备尚未覆盖的M2验证环境和测试脚本。
- 补齐原生125%、键盘、中文输入、PDF像素渲染和迟到事件的可重复实现与证据。
- 如验收发现R1～R5仍有实现缺口，先修样板／契约，再提交新的M2修订记录。
- M2复核通过前不开始M3真实模型接入。

## 五、状态写法

- “开发已实现”：开发报告的事实描述。
- “工程验证通过”：指定脚本在指定环境通过。
- “复核通过”：我已独立复跑并确认该项满足当前验收标准。
- “用户确认”：用户明确给出的产品／视觉／操作反馈。
- “M2整体通过”：所有必要项均有证据、用户完成产品层确认，且没有未披露阻塞。

这些词不能互换。任何一项未运行、仅静态检查或只用Mock验证，都必须保留对应限定。

## 六、路线纠偏（2026-11-24）

本轮复核发现流程出现反向偏移：M2原本用于确认长解释、中央关联、对象隔离和锚点契约，却逐渐扩展成必须先完成全部视觉、原生缩放、中文输入、PDF像素和迟到事件验收，导致开发反复停留在修复／验收循环。

从本条起：

- M2只收口M3必需的设计与契约：解释目标冻结、题目／资料身份隔离、来源失效不误定位、短答与长答入口、页／题任务锚点和回退语义。
- 100%桌面无溢出作为当前样板工程证据保留；原生125%、完整Tab／中文IME、真实PDF像素和复杂迟到事件转为并行质量验证项，不再作为M3方案设计的无限阻塞。
- M3采用有边界的alpha切片：短答、用户明确要求的完整讲解、已核验来源定位、题目上下文冻结与历史只读；不同时实现图片、跨资料自主检索、网络来源、永久贴条和双向链接。
- 未完成的质量项继续列为“未验证”，不能写成“通过”；但未验证本身也不自动否定已确认的M3设计方向。
- 新增验收项目必须说明它阻塞哪一条M3行为；没有直接阻塞关系的项目进入并行质量队列，不再追加到M2主门槛。
