# M3-alpha 独立复核结论

日期：2026-11-24。复核范围：M3-alpha实施报告、服务端生成契约、前端发送与追问、隔离测试和构建。未调用真实模型、未发送个人资料、未迁移正式库。

## 结论

M3-alpha核心实现已存在，不能判定为“未实现”；但本轮发现一个预算预检问题，需要开发修正后再标记alpha通过。其余已复核的状态隔离与请求关系符合任务书的主要方向。

## 已通过的复核项

- `answer_mode=short|complete` 在服务端请求意图中保存；完整模式实际传给网关 `max_tokens=6000`，短模式使用1500。
- 完整讲解和继续追问的生成生命周期测试通过；继续追问使用新request_id并保存`continuation_of`。
- 服务端拒绝不同Topic、未发布父请求或不存在父请求的续问父级；父请求的冻结上下文不被改写。
- 前端查看、引用定位和重读不主动生成；已发布消息显示“继续追问（新请求）”，发送前沿用当前冻结主题与附件。
- 上下文trace、历史范围、来源版本和用户纠正关系仍走原有服务端校验。
- `npm test`：12个测试文件、56项通过；`npm run build`通过；`test_assistant_generation.py`和相关网关测试通过；全后端此前279项通过。

## 必须修改的问题

### M3-01 预算预检对短答过度保守

`backend/app/assistant_generation.py`在真正计算本请求模式之前，使用 `INPUT_LIMIT + COMPLETE_OUTPUT_LIMIT` 作为所有请求的最低剩余预算要求。结果是：即使请求是短答、实际只需1500输出token，只要剩余预算不足完整讲解的6000上限，短答也会被提前拒绝。

影响：短答／完整讲解的意图区分在预算紧张时不成立；短问题可能被错误提示“模型预算不足”，用户无法使用仍有额度的短答。

建议修复：预检根据 `r.intent.answer_mode` 选择对应输出上限；网关最终reservation继续使用实际 `max_tokens`。例如短答预检为 `INPUT_LIMIT + OUTPUT_LIMIT`，完整讲解预检为 `INPUT_LIMIT + COMPLETE_OUTPUT_LIMIT`。如果产品明确要保守预留完整额度，也必须在契约中说明短答会共享完整档位并补测试；当前M3任务书没有这个限制，因此默认按意图区分。

新增回归：设置课程／日预算只剩“输入上界＋短答上限”但少于“输入上界＋完整上限”时，短答必须派发，完整讲解必须被预算保护拒绝；检查provider调用和UsageRecord预留值。
